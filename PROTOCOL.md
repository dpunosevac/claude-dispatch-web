# claude-dispatch protocol (v1)

Copy of §3–§5 of the canonical spec in the private listener repo. Do not edit here; change it there, regenerate the test vectors, and copy both files over.

## 3. Crypto & wire format

### 3.1 Key
- 32 random bytes, shared as **base64url without padding** (43 characters).
- Generated by `cdispatch keygen`.
- **Mac:** stored in the login Keychain (service `claude-dispatch`, account `key`) via `/usr/bin/security`. The key is passed over stdin (`security -i`), never in argv, and never written to the config file.
- **Phone:** entered once and imported as a **non-extractable** WebCrypto `CryptoKey` stored in IndexedDB. Never kept as plaintext in localStorage.

### 3.2 Sealing (both directions)
```
plaintext_json = UTF-8 JSON of the inner message (§4)
compressed     = gzip(plaintext_json)
iv             = 12 random bytes (new for every message)
aad            = "cd1|req"  for phone→Mac   |   "cd1|res" for Mac→phone
ct             = AES-256-GCM(key, iv, compressed, aad)   # includes 16-byte tag
envelope       = {"v":1,"d":"req"|"res","iv":b64(iv),"ct":b64(ct)}
```
- `b64` = standard base64 with padding.
- The AAD binds the direction, so a response can't be replayed as a request.
- Compression comes **before** encryption.
- Browser: `CompressionStream("gzip")` / `DecompressionStream("gzip")` and `crypto.subtle` AES-GCM. Rust: `flate2` + `aes-gcm`.
- Opening: parse envelope, check `v` and `d`, base64-decode, AES-GCM decrypt with the matching AAD, gunzip (capped at 32 MiB), parse JSON. **Silently drop** any message that fails at any step. Never reply to garbage.

### 3.3 Freshness / replay
Every inner message has `id` (128-bit random, hex) and `ts` (unix seconds).
- **Mac (requests):** reject if `|now - ts| > 600` seconds, or if `id` has been seen before. Seen IDs live in SQLite and are pruned after 1 hour (longer than the freshness window, so a replay can never slip through).
- **Page (responses):** the page backfills up to 12 h of responses on load, so it does not apply the 600 s window. It dedupes by `id` and merges by `(turn, ts, state rank)` per job, so a replayed or late response can never move a job backwards. Responses carry no authority (they only update the display), which is why this is safe.

### 3.4 Size limits
- An ntfy message body must stay **≤ 3800 bytes** (ntfy's limit is 4096).
- If a sealed response envelope would be larger, it is sent as an attachment (§5.3).

### 3.5 Test vectors
`protocol/test-vectors.json` contains the key, and per vector: direction, AAD, IV, plaintext, a gzip of the plaintext, and the envelope. Plus `negative` cases that must fail to open (wrong direction, flipped `d`, tampered ciphertext, wrong key).
- gzip output differs between libraries, so vectors test **decryption plus decompression of a fixed ciphertext**; Rust additionally reproduces its own envelopes byte for byte from the fixed IV. Both test suites do a full seal-then-open round trip (200 KB).
- Both `cargo test` (private repo) and `node tests/test-vectors.mjs` (web repo) must pass against the same file.

## 4. Inner messages

Common fields on every message: `id`, `ts`, `type`, `from` (`"phone"` or the machine name).

### 4.1 Requests (phone → `REQ_TOPIC`)

| type | fields | behaviour |
|---|---|---|
| `run` | `job` (8-char random id from phone), `work` (string), `target?` (machine), `prompt` (e.g. `"/ship ABC-123"`) | Start a new Claude job |
| `reply` | `job`, `text` | Resume the job's Claude session with `text` |
| `cancel` | `job` | Kill the running process (or drop it from the queue); state → `cancelled` |
| `ping` | — | Every Mac replies with `hello` |
| `history` | `since?` (unix ts), `limit?` (default 50, max 500) | Each Mac replies with `history` |
| `fetch_result` | `job`, `turn?` (default: latest) | The owning Mac re-sends a `result` message (attachment if large) |
| `sessions` | `target?`, `work?`, `limit?` (default 15, max 50) | The target (or every Mac with `work`) lists recent Claude sessions in its repos, including ones started in a terminal |
| `adopt` | `target`, `job`, `work`, `session_id`, `fork?` (default false) | The target turns that session into job `job` (state `done`, turn 0 = the session's last messages). Replies resume **that same session** (`--resume <id>`), so the laptop sees the phone's turns after `claude --resume <id>`; an open terminal on the session must be exited first, or the two histories interleave. With `fork: true` the first reply adds `--fork-session` and later replies continue the copy, leaving the original untouched |

**Routing (Mac side):**
- **`run`:** act only if `work` is in this Mac's `repos` map **and** (`target` is empty or equals `machine`). Otherwise ignore silently. A `job` id that already exists is ignored.
- **`reply`, `cancel`, `fetch_result`:** act only if the job exists in this Mac's DB.
- **`ping`, `history`:** every Mac answers.
- If two Macs share a `work` id and `target` is empty, both would run the job. The page forces a target choice in that case (it knows which Macs have which work ids from `hello`).
- A `reply` is accepted when the job is `needs_input`, `done` or `failed` and has a `session_id`. A reply to a job that is still `queued`/`started` gets `busy_rejected` with `error`.

### 4.2 Responses (Mac → `RES_TOPIC`)

| type | fields |
|---|---|
| `status` | `job`, `machine`, `work`, `state`, `turn`, `session_id?`, `summary?` (≤ 1500 characters), `question?`, `cost_usd?`, `duration_s?`, `attachment?` (bool), `error?` |
| `hello` | `machine`, `works` (list of work ids), `version`, `busy_jobs` (list), `battery?` (`{pct, charging}`), `sleep_disabled?` (bool, `pmset -g` SleepDisabled) |
| `history` | `machine`, `jobs`: list of `{job, work, prompt, state, created, updated, turns}` (no bodies) |
| `result` | `job`, `machine`, `turn`, `input`, `result` (full text, STATUS line stripped), `log_tail` (last 4 KB of stderr) |
| `sessions` | `machine`, `sessions`: list of `{session_id, work, updated, title, last, origin ("terminal"\|"headless"), job?}` |

**`state` values:** `queued`, `started`, `needs_input`, `done`, `failed`, `cancelled`, `busy_rejected`.

**`turn`:** 0 for the initial run, incremented on each `reply`.

For `needs_input`, the text goes in `question`; otherwise in `summary`. When the text does not fit inline, `attachment: true` is set, the inline text is truncated (≤ 600 chars), and the full text arrives as a `result` attachment.

## 5. ntfy usage

### 5.1 Subscribe (Mac)
- `GET https://ntfy.sh/<REQ_TOPIC>/json` returns a streaming NDJSON connection.
- Handle `event: open | keepalive | message`. Keepalive arrives about every 45 s, so the read timeout is 90 s.
- On reconnect, and across restarts (the last message id is stored in SQLite), use `?since=<last message id>` so nothing is missed. Messages older than 600 s still get rejected by the freshness check.
- Exponential backoff from 1 s up to 30 s.

### 5.2 Publish response (Mac)
`POST https://ntfy.sh/<RES_TOPIC>` with the envelope JSON as the body, plus these headers:
- `Title: Job update`, or `Needs your input` when `state=needs_input`. **No job details in headers.**
- `Click: <page_url>#job=<job>`
- `Priority: high` for `needs_input` and `failed`, `default` for other statuses. `hello`, `history` and `result` use `Title: Machine update` and `Priority: min` so they don't buzz the phone (except the battery warning: `Battery low`, `high`).
- `Tags`: `question` / `white_check_mark` / `x` / `rocket` / `computer` / `battery` (generic only).

### 5.2.1 Quiet topic
Responses that should not notify the phone (`hello` replies to `ping`, `history`, `sessions`, `result` for `fetch_result`) go to `<RES_TOPIC>-quiet`. The ntfy phone app subscribes only to `RES_TOPIC`; the page subscribes to both (`/<RES_TOPIC>,<RES_TOPIC>-quiet/sse`). `status` messages and the battery warning always go to `RES_TOPIC`.

### 5.3 Large results
1. Seal the `result` message exactly like any message, giving envelope bytes.
2. `PUT https://ntfy.sh/<RES_TOPIC>` with the envelope bytes as the body, plus headers:
   - `Filename: r.bin`
   - `X-Message: <small sealed status envelope with attachment:true>` (kept ≤ 2000 bytes)
   - `Title`, `Priority`, `Tags` and `Click` as in §5.2.
3. The page sees `event.attachment.url`, fetches it, opens the envelope, and merges the result.
- Any other response that seals to more than 3800 bytes (e.g. a long `history`) is sent the same way with a plain `X-Message: Open the page to view`.
- If the attachment upload fails, the Mac posts the short status inline; the page can then send `fetch_result`.

**Verified against ntfy.sh:** `X-Message` accepts a sealed envelope of ~1.2 KB; attachment URLs (`https://ntfy.sh/file/...`) are served with `Access-Control-Allow-Origin: *`, and publishing to topics answers CORS preflight with `*`. The chunked fallback is therefore not implemented.

ntfy.sh keeps messages for about 12 h and attachments for a few hours. That's fine, because SQLite on the Mac holds everything permanently.
